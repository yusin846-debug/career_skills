# Yusin Resume Feedback

채용담당자 관점에서 탈락 우려와 근거 부족을 먼저 찾고, 지원 직무에서 재현 가능한 역량이 드러나도록 수정한다. 합격을 보장하거나 근거 없는 JD 적합도·합격 확률을 숫자로 제시하지 않는다. 검토만 요청받았다면 피드백을 제공하고, 수정 요청 시 수정본을 만든다. 실제 지원용 산출물은 PDF이며 수정 가능한 원본은 별도로 남긴다. 이 스킬 자체를 수정하는 작업에는 PDF 출력이 필요하지 않다.

## 1. 검토 기준 확보

- 최신 이력서, 사용자 확인 사실·증빙, 지원 회사와 직무, 공식 공고, 현재 지원서 입력값을 구분한다. 과거 대화의 AI 답변은 사실 증빙으로 취급하지 않으며 개인 정보·연락처·경력 수치를 이 스킬에 고정하지 않는다.
- 회사 공식 채용 사이트 또는 그 사이트에서 연결된 공식 ATS의 **해당 공고 본문**을 열어 직무명, 지역, Job ID, 업무, 필수·우대 요건, 모집 상태를 대조한다. 검색 결과 요약, 유사 직무, 팀 소개로 대신하지 않는다.
- 공식 URL과 확인일, 공고 식별 정보는 별도 검토 기록에 남긴다. 공고가 없거나 접근이 막히면 제공된 JD로 잠정 검토를 계속하되 ‘공식 JD 미확인’으로 표시한다. 정확한 공고 확인 전에는 JD 대조 완료나 제출 준비 완료를 선언하지 않는다.
- 각 주요 요건을 `공식 JD 요구 → 이력서 근거 → 직접 경험/전이 가능한 경험/미확인·공백 → 수정 방향`으로 연결한다. 필수 요건 공백과 단순 표현 개선을 구분한다.

## 2. 내용 QA

### 채용 관점과 경력의 범위

- 20~30초 안에 기억할 포지셔닝 한 문장을 먼저 판단한다. 창업 경력은 숨기거나 훈장처럼 앞세우지 말고 실제 실무·협업·문제 해결 근거로 연결한다.
- 직무·직급 적합성, 경력 과잉·부족, 전환 이유, 조직 적응·근속 우려를 검토한다. 우려는 문서에서 생길 수 있는 해석으로 설명하며 사용자의 의도나 성향을 단정하지 않는다.
- 외국계 IT는 실제 JD에 따라 SDR/BDR의 발굴·qualification, AE의 제안·협상·계약, AM의 유지·확장, Partner Sales의 파트너 프로그램, Sales Ops의 분석·보고·프로세스를 구분한다. 리테일은 현장·매출·견적·운영·고객 경험·협력업체 조율 중 해당 JD의 요구를 우선한다.
- 회사·팀 지표와 개인 성과를 분리하고 기간, 단위, 누적/연간, 분모, 대략값 여부와 본인의 책임 범위를 확인한다. 회사 매출을 개인 실적으로, 일반 연매출을 ARR로 바꾸지 않는다. 근거 없는 인과관계나 단독 기여를 추가하지 않는다.
- 당시 한 일은 실제 범위의 언어로 쓴다. 설치·물류 업체 조율을 partner ecosystem 구축으로, 퍼널 확인을 forecasting 또는 RevOps 운영으로 확대하지 않는다. 직무 용어는 실제 수행 방식이 뒷받침할 때만 사용한다.
- 교육·자격·POC와 상용 업무 경험을 분리한다. Salesforce 교육을 과거 직장의 Salesforce 운영 경력으로 소급하지 않는다. 부족한 경험은 공백으로 남기고 유사 경험의 전이 가능성을 설명한다.
- 문장별로 필요할 때 `[유지/수정/삭제]`, 이유, 사실 범위 안의 대체 문장을 제시한다. JD와 무관한 좋은 경력, 반복 섹션, 숫자 과밀을 줄인다.

### 사실 및 지원서 일치

- `항목 | 확인 근거 | 이력서 표기 | 지원서 입력값 | 판정·조치`로 대조한다. 지원서를 아직 보지 못했다면 해당 검증은 미확인으로 남긴다.
- 이름·연락처, 회사명·직함·재직 기간·고용 상태, 학교 공식 명칭·전공·재학 기간·학위 취득 여부를 확인한다. 대학 이수·수료를 학위 취득으로 바꾸지 않는다.
- 지원서 학력 선택지는 질문 전체와 실제 옵션을 읽고 판단한다. 적합한 비학위 옵션이 없다고 임의로 학사·전문학사를 선택하거나 대학명과 고교 졸업값을 모순되게 결합하지 않는다. 공식 안내·설명란을 확인하고 해결되지 않는 필수 입력은 사용자 확인 사항으로 남긴다.
- 자격증의 공식 명칭·발급기관·취득일·유효 상태·필요한 식별자를 증빙과 대조한다. 교육 수료·수상·시험 준비를 자격증으로 분류하지 않는다. 이력서에 있어도 별도 필수 자격증 입력란은 따로 검토한다.
- 언어 수준·시험 점수·취득일을 확인한다. 학습 목표나 시험 준비를 현재 업무 가능 수준으로 쓰지 않는다. 단순 언어명 표기로 필수 fluency 요건 충족을 판정하지 않으며 직접 질문에는 실제 수준을 답한다.
- 근무 자격, 비자 지원, 이전 지원·근무 이력, 정부기관·군 복무 등은 질문의 기간·정의·선택지를 사용자 사실과 대조한다. 이전 지원의 답을 복사하지 않는다. 문항이 모호하면 공식 안내를 확인하고 사실이 없으면 답을 추정하지 않는다.

### 문체

자신감 있고 단정하지만 예의와 겸손이 밑바탕에 있는 ‘믿음직한 세일즈맨’의 톤을 유지한다. 한국어는 ‘만들었습니다/조율했습니다’처럼 1인칭 직접 서술을 사용하고 명사형 수동 표현을 피한다. 영어도 행동 주체와 실제 기여가 명확한 능동 문장을 쓴다. 자기평가 수식어나 단독 영웅담 대신 문제·행동·협업·결과를 담담하게 제시한다.

## 3. 디자인 QA

- 디자인 수정 전에 지원 회사의 공식 브랜드 가이드·공개 디자인 시스템을 조사한다. 정확한 토큰명과 값, 버전·테마·상태, 타이포의 font family/weight/size/line-height/letter-spacing, 관련 컴포넌트 규격을 출처 URL과 함께 별도 기록한다. 이전 회사의 값이나 과거 대화의 값을 재검증 없이 재사용하지 않는다.
- 공식 로고·포인트 컬러, 배지/pill, 카드형 강조 지표 등 실제 컴포넌트 중 문서에 필요한 것을 적용한다. 토큰을 임의로 추측해 ‘회사 공식 색상’으로 부르지 않는다. 공개 규격이 없으면 공식 사이트에서 확인한 스타일과 자체 조정값을 구분하고, 폰트 대체나 웹 단위의 PDF 변환도 기록한다.
- 얇고 읽기 쉬운 글꼴, 여유 있는 자간, 충분한 섹션 간격, 페이지 상하 균형, 절제된 장식을 유지한다. 브랜드 재현 때문에 본문 대비·가독성을 희생하거나 카드·로고로 지표를 과시하지 않는다.
- 실제 PDF의 모든 페이지를 이미지로 렌더링해 정상 읽기 크기와 확대 상태에서 확인한다. 줄바꿈·글자 누락·겹침·잘림, 폰트 대체, 행간, 정렬, 고립된 제목, 페이지별 정보 밀도·여백과 중복 표기를 확인한다. 추출 텍스트가 정상이라는 이유로 디자인 QA를 통과시키지 않는다.

## 4. 제출물 QA — 실제 최종 PDF에 수행

내용 QA와 디자인 QA 통과는 제출물 QA의 대체가 아니다. 업로드할 파일 경로·파일명·수정 시각 또는 해시를 기록하고 아래 검사를 **그 파일**에 수행한다.

### 내부 작업 흔적 제거

- 제출 PDF의 본문·머리말·꼬리말·메타데이터·주석·북마크·첨부에 TARGET, Job ID, 내부 검토 메모, 수정 지시, placeholder, 이전 지원 회사명이 남아 있지 않은지 검사한다. 대소문자·공백 변형과 해당 공고의 실제 ID도 찾고 렌더링으로 재확인한다.
- `TARGET · 직무 · 회사 · JOB ID` 같은 내부 타깃 줄은 제거한다. 정상적인 영업 목표 의미의 target이나 정식 자격증 식별자를 기계적으로 삭제하지 않는다. 지원동기에 필요한 회사명과 불필요한 반복 노출을 구분한다.

### 연락처 링크: 기능과 시각을 각각 통과

- 사용자 확인 LinkedIn 프로필 URL, 이메일, 전화번호를 사용한다. 링크를 추측하지 않는다. 표시된 LinkedIn/email/phone에 각각 HTTPS, `mailto:`, `tel:` 링크를 설정한다. 표시 번호와 국제 형식 목적지가 같은 번호인지 확인한다.
- PyMuPDF의 `page.get_links()` 또는 동등한 PDF 파서로 최종 PDF의 실제 link annotation을 검사한다. 각 링크의 페이지, URI 목적지, 클릭 영역(rect)이 올바른 텍스트를 덮는지 확인한다. 원본 HTML의 href나 뷰어 자동 감지만으로 통과시키지 않는다.
- 렌더링된 PDF에서 링크가 **클릭 가능하게 보이는지** 따로 확인한다. 본문과 구별되는 충분한 대비의 링크 색상과 밑줄 등 명확한 단서를 사용한다. 파란 글씨만 있고 annotation이 없거나, annotation만 있고 일반 텍스트처럼 보이면 실패다.
- 가능한 경우 PDF 뷰어에서 직접 열어 클릭 영역과 목적지 동작을 확인한다. 이메일·전화는 작성/통화 진입까지만 확인하며 메시지 전송·통화 실행은 하지 않는다. 뷰어 또는 외부 앱 동작을 시험하지 못했으면 파서 검사 결과와 구분해 보고한다.

### 마지막 검수

- 최종 내보내기 후 모든 페이지를 다시 렌더링하고 링크 annotation, 텍스트 추출·읽기 순서, 페이지 수, 파일명, 레이아웃을 확인한다. 마지막 수정 이후에는 이전 파일의 검수 결과를 재사용하지 않는다.
- PDF를 다시 열 수 있는지 확인하고, 포털의 실제 파일 형식·크기 제한과 업로드된 파일명·미리보기까지 확인한다. 자동 추출된 학력·경력·연락처는 원본과 다시 대조한다. 업로드 후 검사를 못 했다면 별도로 미확인 표시한다.
- QA 기록은 제출 PDF 밖에 보관한다. 실제 지원 제출은 사용자가 승인한 범위에서만 실행하며 피드백 요청을 제출 권한으로 해석하지 않는다.

## 5. 결과 보고와 완료 기준

핵심 채용 관점 판정, 근거 있는 우려, 우선 수정할 문장, 남은 사실 확인을 짧게 보고한다. 문제에는 위치·증거·조치를 붙이고 다음 세 상태를 독립적으로 표시한다.

| 검증 | 상태 | 근거 |
| --- | --- | --- |
| 내용 QA | 통과 / 수정 필요 / 미확인 | 공식 JD 대조, 사실·기여 범위, 지원서 일치 |
| 디자인 QA | 통과 / 수정 필요 / 미확인 | 공식 스타일 출처, 실제 전체 페이지 렌더링 |
| 제출물 QA | 통과 / 수정 필요 / 미확인 | 최종 파일 식별, 내부 흔적, 링크 기능·시각, 업로드 확인 |

검토만 요청된 경우 수행하지 않은 단계는 ‘이번 범위 밖’으로 표시한다. 자료 누락·접근 불가·도구 부재를 통과로 처리하지 않는다. ‘PDF 검수 완료’, ‘지원서 일치 확인’, ‘업로드 확인’을 구분하고, 필수 검증이 남으면 포괄적인 ‘바로 제출 가능’ 판정을 하지 않는다. 발견한 오류의 채용 결과 영향을 근거 없이 축소하거나 확대하지 않는다. 수정본을 만들었다면 검수한 최종 PDF 링크와 원본 링크를 제공한다.
